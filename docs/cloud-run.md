# Cloud Run release

Only Google Cloud project `tough-melody-508008-p8` is authorized. `deploy/gcp.ps1` defaults to an offline plan; `-Inspect` reads that project only. Actual `-Execute` needs a prior, recorded spending decision, a clean committed checkout and existing CLI authentication. It runs essential tests and a local image smoke check before upload. Use `-Resume` after an interrupted step; inspect any uncertain resource creation rather than overwriting a collision.

Dedicated resources: service `holdthat`, registry `holdthat-images`, runtime identity `holdthat-runtime`, and private bucket `tough-melody-508008-p8-holdthat-sessions`. The runtime has Object User on its own bucket only. No key files, Firebase/SQL, domains, Cloud Build, existing-app resources or AWS secrets are needed. Request-based billing, min 0/max 1, 1 CPU/512 MiB, concurrency 16. These settings and process admission limits are not a guaranteed financial cap.

The app selects `HOLDTHAT_STORE=gcs` on Cloud Run, refuses SQLite there, and authenticates through its attached identity. Each hashed browser owner has one bounded JSON object containing state and retry identities. Reads take the body and exact generation from one response; writes and deletes carry generation preconditions. Racing revisions fail safely; retries return current progress; stale session tokens cannot mutate/delete a replacement. Seven days of inactivity expires a session. Lifecycle age 7 removes idle objects asynchronously; soft delete, versioning and retention are disabled only on this new bucket. No browser data is stored in the image or ephemeral filesystem. SQLite remains available for local volumes.

Storage failures return a safe retry message and never fall back to blank local state. CRC32C checks protect transfers. Sessions are capped at 1 MiB; export/clear if full. Per-process API admission is 600 requests/minute, new session attempts 1000/day, plus per-owner 120/minute. Restarts reset these counters, so they are abuse mitigation, not quota accounting.

The script first creates a restricted revision, reads its actual HTTPS URL, then sets the exact canonical origin. After authenticated live REST/MCP checks, publish with `-Execute -Resume -Publish`. `scripts/verify-live.ts` verifies the release; no deployment is marked complete from health alone. A second revision plus the saved probe session verifies persistence.
